# Learn one Sushi idea when you need it

The [Build recipes](<../build/README.md>) show how to get work done. Use this page when you want to
understand why the pieces are separated that way. The topics are independent lookups, not another
required course.

| Question | Focused explanation |
|---|---|
| Who owns hardware, controls, policy, status, and composition? | [Robot roles](<learn-sushi/Robot Roles.md>) |
| How does a button or joystick become robot intent? | [Controls and intent](<learn-sushi/Controls and Intent.md>) |
| How does intent become one bounded hardware command? | [Plants and hardware](<learn-sushi/Plants and Hardware.md>) |
| How does work continue without sleeping or blocking? | [Tasks and autonomous](<learn-sushi/Tasks and Autonomous.md>) |
| What does a software test, sensor, or experiment actually prove? | [Evidence and experiments](<learn-sushi/Evidence and Experiments.md>) |
| Which owner should change for a new requirement? | [From requirement to robot](<learn-sushi/From Requirement to Robot.md>) |

If this is your first contact with Sushi, begin with
[Sushi in one picture](<Framework Overview.md>). If you already know the concept and need an exact
signature, go to the [categorized reference](<../reference/README.md>) or
[API type/member search](<https://harishv-99.github.io/2025-PhoenixPedro/api/>).
