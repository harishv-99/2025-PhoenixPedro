# Learn one Sushi idea when you need it

Start in software, with the teaching OpModes still disabled:

1. Read [how Sushi runs your code](<Framework Overview.md>) to connect it to an FTC loop you already
   know.
2. [Set up and verify the Sushi project](<Build and Run.md>).
3. Follow the [First software tour](<First Software Tour.md>) through live drive values, one button
   press, and one timed Auto. No matching robot is required.

After that short route, use this page only for the question in front of you. These are explanations,
not another required course.

| What do you want to understand? | Read this |
| --- | --- |
| What happens between `gamepad1.a` becoming pressed and the intake motor command? | [Controls and intent](<learn-sushi/Controls and Intent.md>) |
| Where should motor names, button meanings, shared robot actions, and hardware code live? | [Robot roles](<learn-sushi/Robot Roles.md>) |
| How does one requested action become one checked motor or servo command? | [Plants and hardware](<learn-sushi/Plants and Hardware.md>) |
| How can Auto continue work over several loops without sleeping or freezing the robot? | [Tasks and autonomous](<learn-sushi/Tasks and Autonomous.md>) |
| How can I tell what a software test, sensor reading, or hardware experiment really proved? | [Evidence and experiments](<learn-sushi/Evidence and Experiments.md>) |
| When a new robot requirement arrives, which part of the program should change? | [From requirement to robot](<learn-sushi/From Requirement to Robot.md>) |

When you are ready to work with hardware, choose only the next outcome your robot needs from the
[Build recipes](<../build/README.md>). Each recipe keeps the software check before its separate,
supervised hardware gate; the entire actuator sequence is not a prerequisite for an unrelated goal.

If you already know the concept and need an exact signature, use the
[categorized reference](<../reference/README.md>) or
[API type/member search](<https://harishv-99.github.io/2025-PhoenixPedro/api/>).
